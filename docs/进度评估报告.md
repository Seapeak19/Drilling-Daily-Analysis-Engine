## 五、发现的问题

### 5.1 【高】`events[].hours` 把钟点误判为时长

#### 现象

解析任一份样本日报，`events[].hours` 的数值均不合理：

```
hours=6.0    span='06'   06:45 钻进至 1939.19 m，钻压 122 kN，转速 1...
hours=9.0    span='09'   09:00 接单根，耗时 18 分钟。
hours=12.0   span='12'   12:30 循环调整泥浆性能，密度提至 1.14 g/cm3...
hours=15.0   span='15'   15:45 起钻至 1904.69 m，期间无遇卡显示。
```

- `06:45 钻进至 1939.19 m` 的正确结果是 `None`（该备注未叙述任何时长；
  文中 `钻时 15.8 m/h` 是**钻速不是时长**）
- `09:00 接单根，耗时 18 分钟` 的正确结果是 `0.3`（18 分钟），实测 `9.0`
- `13:00 顶驱故障，停钻 4.0 小时` 的正确结果是 `4.0`，实测 `13.0`

#### 根因

`src/ddr/llm.py:53` 的正则：

```python
_NUM_UNIT_RE = re.compile(
    r"(?P<num>\d+(?:\.\d+)?)\s*(?P<unit>小时|h|hr|hrs|分钟|min|minutes|天|day|days|m|米|ft)?",
    re.IGNORECASE,
)
```

三层缺陷叠加：

1. **`unit` 是可选的**（`?`），且单位池含 `""` 分支——裸数字被当作"小时"处理
   （`llm.py:91`：`if unit in ("小时", "h", "hr", "hrs", "")`）
2. **正则非贪婪地从左往右取"第一个能被解释为小时的数字"**，
   而真实日报备注**几乎必然以钟点开头**——`06:30` 的 `06` 先被命中
3. **`re.search` 匹配 `06:30` 时，`06` 之后的 `:` 不构成边界障碍**，
   因为单位组是可选的，匹配在 `06` 处即成功

#### 护栏为何失效（这一层最值得警惕）

`_verify_span`（`llm.py:101-105`）的职责是"数值必须在原文逐字出现，
否则丢弃"，本意是防 LLM 幻觉。但它在这条路径上**为错误结果背书**：

```python
def _verify_span(text: str, span: str | None) -> bool:
    if not span:
        return False
    return span in text          # '06' in '06:45 ...' → True
```

`span` 是裸串 `'06'`，在 `'06:45'` 中必然命中，于是 `verified=True`。
**输出因此带上了"已验证"标记，而实际是错的**——这比直接失败危险得多，
正是项目自己在 README 中反对的"静默降级产出看似正常、实则错误的 JSON"。

对照：正确的匹配（`2.5 小时处理井漏` → `span='2.5 小时'`）带单位，
所以护栏有效；失效只发生在**匹配到无单位数字**时。

#### 影响面实测

**135 条备注，100% 被污染**：

```
事件总数 135，其中带 hours 数值的 135 条（100%）
```

#### 为什么 231 项测试没抓到

`tests/test_llm_guards.py` 的用例文本**全是手工构造的不带钟点前缀的短句**：

```python
R(1, "井漏，堵漏 2.5 小时")        # → 2.5 ✅
R(1, "接单根，耗时 12 分钟")        # → 0.2 ✅
R(1, "岩性为细砂岩")               # → None ✅
```

这些用例恰好绕开了触发条件。而真实日报的典型句式是
**「钟点 + 动作 + 伴随参数数字」**，从未被任何用例覆盖。
这是一个典型的**测试与实现同源盲区**：用例是照着正则能通过的样子写的，
而不是照着真实文本写的。

#### 影响评级与边界

| 维度 | 判定 |
|---|---|
| 是否污染主链路 | **否**。`time_log` / `time_verification` / `kpi` 与 `events` 相互独立，24h 校验不受影响 |
| 是否污染阶段 2 | **是，且恰好命中要害**。NPT 归因与 ILT 识别都要读 `events[].hours` 与 `npt_category` |
| 是否影响评测可信度 | 部分。`ddr eval` 的 444 项断言**未覆盖 `events`**（评测器只断言到 `npt_events`/`connection_*`），因此 100% 准确率与这个缺陷并不矛盾，但也说明**该字段处于评测盲区** |
| 修复难度 | **低**。改动集中在 `llm.py` 的 `_extract_hours` / `_verify_span`，可用 135 条真实备注立即验证 |

#### 修复方向（建议，未实施）

1. **匹配前先剥离钟点**：`\b\d{1,2}:\d{2}\b` 从文本中移除或标记跳过，
   避免 `06:30` 的 `06` 参与匹配
2. **要求单位非空**：裸数字不再默认按小时处理（去除 `""` 分支），
   或仅在明确的时长语境词（"耗时/停钻/用时/历时"）后才接受裸数字
3. **拒绝带冒号后缀的匹配**：`(?![:\d])` 负向断言，防止匹配到 `06:30` 的 `06`
4. **强化 `_verify_span`**：验证的 `span` 必须**自带单位**，
   否则 `verified` 不得为 `True`——让护栏能识别"这个证据不足以证明是时长"
5. **补充回归用例**，直接用真实句式：
   - `"06:45 钻进至 1939.19 m，钻压 122 kN，钻时 15.8 m/h。"` → `None`
   - `"09:00 接单根，耗时 18 分钟。"` → `0.3`
   - `"13:00 顶驱 VFD 故障，停钻 4.0 小时。"` → `4.0`
   - `"2.5 小时处理井漏。"` → `2.5`（不得回归）

> **注意第 5 条的必要性**：修复必须用**真实句式**做用例，否则会重蹈
> "用例照着实现写"的覆辙。

## 附录 B：更正说明（2026-10-09 补记）

本报告是 2026-10-08 的评估快照，**保留原文不改**，以便对照当时的判断。
但后续动手修复时查明了三处需要更正/补充的地方，如实记录如下。

### B.1 §5.2 对 `time_hint` 的定性有误 —— 根因不在解析器

**原文说法**：「`remarks[].time_hint` 精度截断，`06:30` 被记为 `"06:00"`
（`extract.py` 的时间标记识别）」。

**实际情况**：`time_hint` 的 `"06:00"` **来自日报原文**，是模拟器
（`simulate.py`）刻意写入的"整点桶"标签，不是解析器截断的结果。
真正的缺陷是**同一信息被写了两遍且两个值不一致**：

| 位置 | 值 | 来源 |
|---|---|---|
| `remarks[].time_hint` | `"06:00"` | 模拟器的整点桶标签 |
| 正文开头 | `"06:30"` | 同一句里的真实时刻 |

渲染器把两者拼在一起 → 印出 `06:00　06:30 钻进至…`。

**为什么这个更正重要**：根因在**数据生成端**而非解析端，
所以只修 `llm.py` 是治标。治本方案是让钟点只出现一次、
`time_hint` 由正文派生 —— 这才是 2026-10-09 实际采用的修复。

### B.2 §5.1 的影响面描述需要精确化

原文说"135 条备注 100% 被污染"，这一数字正确，但**补充两点**：

1. 污染只影响 `events[].hours`（与 `npt_category` 的派生判断），
   **不污染主链路**（`time_log` / `time_verification` / `kpi` 相互独立）；
2. 35 条备注确实含明确时长（"耗时 12 分钟"），其余 100 条的 `hours`
   本应为 `None`。旧实现对**全部** 135 条都赋了值。

第 2 点直接影响**测试断言的设计**：只断言"有明确时长的备注其 hours 正确"
（字面量比对）**抓不住**这个缺陷 —— 旧实现恰好在那 35 条上碰对了。
必须同时断言"无明确时长的备注其 hours 必须为 None"（条数比对），
才能让缺陷暴露。这一点已落实到 `evaluate.py` 的
`event_hours_none_ratio` 断言中，并经反向验证确认能抓住旧实现。

### B.3 补充：当时未发现的 `npt_responsibility` 缺口

§5 只列了 `events[].hours`，**漏掉了同一类问题**：
`npt_responsibility`（责任归属）在数据模型、Schema、图表、渲染器里
全部被引用，模拟器也生成了 21 条非空值，但抽取器**从未读取它**
（`extract.py` 硬编码 `None`），评测也不覆盖。

这与 `events[].hours` 是**同一类失效模式**：
**字段看起来实现了，实际没有，而且没有东西能发现它没有。**
详见 `docs/改进报告` 与 README「局限」第 5 条。
