## 〇、先说一条贯穿全文的原则

CI 首次运行时全部任务失败，根因不是"没装字体"，而是**判断标准选错了**：
代码问的是"字体文件在不在"，而真正该问的是"这个字体能不能渲染中文"。
用只含拉丁字形的字体实测：

```
arial.ttf 存在         -> True
reportlab 注册          -> 成功（不抛异常）
渲染"旋转钻进"后读回     -> '\x00\x00\x00\x00 2066.06'    ← 中文变成空字节
```

reportlab 没有字形时**不报错**，只画空字形。于是链式静默失败：
中文全丢 → 模板识别失败 → 时间表找不到 → 只解析出 1 条 `UNKNOWN 24h`。
真正的报错离根因极远，为此浪费了一整轮 CI。

**本项目已有的失效都属于同一族**：

| 失效 | 判断标准错在哪 |
|---|---|
| `events[].hours` 100% 污染 | 护栏判断 `span in text`，而非"这段证据是否足以证明是时长" |
| `npt_responsibility` 恒为 null | 文档/模型/Schema 都有，没人验证"抽取器是否真的读它" |
| 字体渲染不出中文 | 判断"文件存在"，而非"能渲染" |
| 主评测集 100% | ground truth 与 PDF 同源，判断"自洽"而非"读对了" |

所以本计划的每一步都以同一个问题收尾：**这一步的产出，由什么证明它是对的？**
拿不出答案的产出，就是在制造下一个静默失效。

### A3 记录 ILT 基准值方法论 —— 计划书 8.1 列为风险

**为什么现在做**：ILT 是项目的技术护城河（计划书 §2.2），而
"基准值怎么定"直接决定 ILT 机会量化是否可信。计划书要求用
**"已反复实现过的最优值"而非理论极值**，但没给操作定义。

**交付物**：一页决策记录，回答四个问题：

1. 基准取自哪个统计量？（P10 / 历史最优 / 行业参考值？）
2. 样本量不足时怎么办？（当前只有 3 口井）
3. 基准随样本更新时，历史结论怎么保持可比？
4. 报告里如何公开基准来源（计划书要求"公开基准来源"）？

**验收**：`docs/ILT基准值方法论.md`，且阶段 C3 的实现直接引用它。

## 三、阶段 B：让样本配得上分析引擎（约 1–2 周）

> **这一段最容易被跳过，但它决定了阶段 C 的产出有没有说服力。**

阶段 C 要做的 ILT 分布、平点定位、邻井对标，本质都是**统计特征分析**。
而当前样本集有三处已知偏差，恰好让这些指标**测不出真伪**：

| 样本现状 | 对阶段 C 的影响 |
|---|---|
| NPT 率 10.7%（行业基准 20–25%） | 归因帕累托图会很空，排序无意义 |
| 钻头记录仅 6/21 份 | 钻头性能对标无法验证 |
| ILT 信号是**按已知答案植入**的 | 分析器只要"算出差异"就算通过——**自己出题自己答** |

### B1 提升 NPT 覆盖到行业区间

把模拟器的"每天至多注入少量 NPT"改成含长时间停工工况，
目标 `ddr stats` 显示 NPT 率落入 20–25%。

### B2 扩展钻头记录覆盖（6/21 → ≥18/21）

钻头对标需要足够样本，否则 C5 无法验证。

### B3 ⭐ ILT 信号改造：从"植入答案"改为"植入机制"

**这是本阶段的核心，也是整个计划里最重要的一条设计决策。**

现在的做法：给白班设 8 分钟、夜班设 14 分钟的接单根耗时。
分析器只要在两个分组上算均值就能"发现"差异——**但如果分析器写错了
（分组搞反、分位数算错），它依然会算出差异，因为差异本来就是给定的**。

改成：

- 给每个班组设"作业节奏"参数（钻具更换速度、操作熟练度），
  让接单根耗时**从机制中自然涌现**；
- 加入干扰：井下条件波动、井段深度差异、班次轮换；
- 结果：**差异的幅度与方向不由我们指定**，分析器必须真的算对才能复现。

**这与 `test_golden_sample.py` 是同一个思路**（打破"自己出题自己答"），
只是作用在分析层而非解析层。

### B4 增加井数（3 → 8~10 口）

邻井对标需要同深度区间可比井数 ≥5 才有统计意义。
同时应让**不同井的作业效率有系统性差异**（否则对标图是一条平线）。

### B5 同步更新 ground truth 与 manifest

**验收**：`ddr check` 0 问题；`ddr eval` 保持 100%；
`ddr stats` 的 NPT 率与钻头覆盖达到目标；
`ddr robust` 不回归。

> ⚠ **B 段会改动 `data/samples/` 下全部文件**（重新生成样本）。
> 参考本次经验：改完必须用"新旧逐份比对"确认只有预期字段变化
> （本次是除 `time_hint` 外零差异）。这个比对方法应固化成脚本。

## 四、阶段 C：分析引擎（约 3–4 周，对应计划书阶段 2）

按**依赖顺序**推进，而不是按计划书的呈现顺序：

| 顺序 | 模块 | 依赖 | 验收标准 |
|---|---|---|---|
| C1 | 时效分解聚合（跨日报） | — | 单井全周期三类时间占比与趋势；与逐日结果加总一致 |
| C2 | NPT 归因 + 帕累托 | A2, A4, B1 | 按类别降序；责任归属可分组；与 ground truth 逐条一致 |
| C3 | **ILT 接单根分布** | A3, B3 | P25/中位数/P75/P90 与 ground truth `connections[].minutes` 对齐；班组差异可复现 |
| C4 | **ILT 平点定位** | B2 | 进尺-时间曲线平段深度区间与实际低效区间吻合 |
| C5 | 邻井对标 | B4 | 同深度区间 ROP/单位进尺耗时对比；分段（表层/技套/生产/水平） |
| C6 | KPI 单元测试 | C1–C5 | 用合成数据 + **独立复算**验证（不是拿实现验证实现） |

**C3/C4 是项目技术含金量的所在**。建议各自配一组"黄金样本"——
期望值手工写死，不从模拟器反推。

**必须避免的坑**：C6 的测试若引用实现里的常量（如 `from ddr.ilt import BASELINE`），
就等于没测。期望值必须独立复算——`tests/test_units.py` 开头写明了这条纪律。

## 九、每个阶段收尾时都要回答的三个问题

沿用第〇节的原则，作为阶段验收的自检：

1. **这一步的产出，由什么证明它是对的？**
   （测试？独立复算？真实数据？还是"看起来跑通了"？）
2. **如果它错了，谁会先发现？**
   （CI？评测断言？还是等到用户拿到错误结论？）
3. **有没有一处判断的是"存在/看起来有"，而不是"能用/是对的"？**

第 3 问是本次 CI 事故的直接教训。它的通用形式是：

> **判断"能不能"，而不是"看起来有没有"。**
